# Multi-Agent 模拟交易 + 失败归因驱动的提示词进化（design）

> 2026-07-16。给已有的 8 个 LLM 调用加**编排 + 状态 + 记忆**，让 agent 每交易日在多个模拟盘
> 自主交易，从**失败**中提炼可检验的教训，反哺提示词。

## 目标（用户原话）

- 「AI 最好的是学到失败的原因（哪怕最后赚钱是成功的，但是过程的教训也是可以一直学习的）」
- 「成功赚钱的原因有太多了，这个不值得学」
- 「多开一些模拟盘给 AI，允许 AI 每个交易日进行自主的选股买入或者卖出持仓」
- 「多设置一些启动资金档位和同一个档位的资金多设置几笔」
- 「这个模拟的多 agent 我希望能和已经有的 agent 提出建议的那几个功能联动，去优化他们的提示词和流程」
- 「最后最后一定要记得管理存储空间」

## 起点：现状已经是一个 8-agent 系统

```
llm.py — 8 个函数，全部平级、无状态、单次调用、用户手动触发
  market_overview / daily_recommendation / market_screen / position_advice / entry_advice  (v4-pro)
  macro_digest / company_profile / structure_note                                          (v4-flash)
统一 _chat() + _DISCLAIMER，统一注入 _tier_block + _fee_block + _macro_block + _ai_web_context
agent 间唯一通信：macro_digest → _macro_block → 其他 5 个；company_profile → _profile_block → entry/position
```

缺的三样：**编排**（无人自动开工）、**状态**（每次从零）、**记忆**（仅 ai_cache 30min）。
故本设计不是从零搭，是给已有的加骨架。

## 两个决定性认知（推翻了初版设想）

### 1. 统计验证不可能，失败诊断可行

按用户交易频率（1 万本金 · 波段 · 20–30 笔/年）实算：

| 问题 | 需要样本 | 折合时间 |
|------|----------|----------|
| 「这套策略有正期望吗？」（55% vs 50%，α=.05, power=.8） | **784 笔** | **31 年** |
| 60% vs 50% | 196 笔 | 8 年 |
| 「这笔为什么亏？」 | **1 笔** | 立刻 |

**结论：放弃「验证策略优势」，转向「诊断单笔失败」。** 失败归因不是推断概率，是核对事实
（`range_pos=92` 就是追高、赚 0.18% < 保本 0.232% 就是倒贴），客观、即时、不需要样本量。

### 2. 因此「AI 自我优化」必须限定优化目标

| 优化目标 | 样本量 | 客观性 | 反馈延迟 | 可行 |
|----------|--------|--------|----------|------|
| 收益率 | 5–8/季度 | 被大盘 beta 污染 | 数周 | ❌ **拟合噪音，禁止** |
| 引用有效性（`provenance.verify_basis` 的 ✓/⚠） | **每次调用 1 个** | 后端权威校验，AI 编不了 | 立即 | ✅ |
| JSON schema 合规率 / 字段漏填率 | 每次调用 | 客观 | 立即 | ✅ |
| **失败教训命中率**（教训写进提示词后，同类错误是否减少） | 每次决策 | 可客观判定 | 数日 | ✅ |

**红线：绝不让优化器朝收益率进化提示词。** 大盘涨 10% 时 AI 随便买都赚，优化器会学到「AI 很棒」。

## 架构：职能流水线 + 可插拔决策

```
每交易日 (launchd 触发)
┌─ 盘前 09:00 ──────────────────────────────────────────────┐
│ ① 研判 agent   复用 llm.market_overview + macro_digest     │
│                → {今日攻防, 关注板块}                       │
└───────────────────────────────────────────────────────────┘
┌─ 盘中 09:35 ──────────────────────────────────────────────┐
│ ② 选股 agent   复用 app._screen_rows(板块) + _pa_score     │
│                → 候选 N 只                                 │
│ ③ 决策 agent   **可插拔**（见下）→ 买卖意向                 │
│ ④ 风控 agent   仓位上限/单笔风险/现金下限 (tier template)   │
│                → 否决或调整                                │
│ ⑤ 下单         paper_store.order()（真实撮合+真实费率）     │
└───────────────────────────────────────────────────────────┘
┌─ 盘后 15:30 ──────────────────────────────────────────────┐
│ ⑥ 复盘 agent   只对**亏损/违规**决策做归因 → 教训           │
└───────────────────────────────────────────────────────────┘
```

### 决策步可插拔（用户明确要求）

`decide(ctx) -> list[Order]` 是稳定契约，上下游不关心内部实现：

- `SingleDecider`（第一版）：一次 v4-pro 调用。
- `DebateDecider`（预留）：多头 + 空头**并行** → 裁判。两轮 ≈ 120s，不是 3×。

两者的归因数据落同一张表，可直接 A/B。**理由**：技术上都不难，但同时上两个未验证的东西
出问题无法归因——而归因正是本设计的全部价值。先跑 Single 拿基线，用数据证明需要辩论再换。

## 多模拟盘并行 = 穷人的平行实验

用户要「多资金档位 + 同档位多笔」。这同时解决两件事：

- **档位维度**：微型/小型/中型… 各开账户，验证 `profile_store` 的 5 档 template 是否真的适配。
- **同档重复**：同一档开 N 个账户跑同一天 → 看**方差**（同样的输入，AI 的输出稳不稳）。
- **样本量 × N**：10 个账户 = 10 份独立失败样本/天。不能解决 784 笔问题，但显著加速教训积累。

每个 agent 账户绑一个 `profile`（含**费率**），故成本模型自动跟随，无需额外配置。

## 教训库（核心）

```sql
CREATE TABLE lessons(
  id INTEGER PRIMARY KEY,
  created_at TEXT, account_id INTEGER, code TEXT,
  kind TEXT,          -- chase_high|below_breakeven|against_sector|rule_violation|oversize|...
  rule_id INTEGER,    -- 违反了 rules_store 的哪条（可空）
  evidence TEXT,      -- 客观事实：range_pos=92 / 收益0.18%<保本0.232%
  lesson TEXT,        -- 一句话教训
  hits INTEGER DEFAULT 1,   -- 同类累计次数
  last_seen TEXT
);
```

**只记失败，不记成功**（用户判断：成功多为 beta，学之即噪音）。
`kind` 是**闭集**——参照 `provenance.SIGNAL_DEFS` 的做法，让教训可统计、可校验，
而非自由文本。同 kind 累加 `hits`，进提示词时按 hits 排序取 Top-N。

反哺方式（**不是让 AI 改写提示词**，而是把事实统计喂进去）：

```
【历史教训（你过去的真实错误，按发生次数排序）】
- 你在 range_pos>90 时买入 7 次，其中 6 次亏损 → 避免在 20 日区间位置 >90 时建仓
- 你有 4 次卖出收益 <0.232%（保本线），实际倒贴手续费 → 不要为小于保本涨幅的价差进出
```

这是**事实统计**，不是拟合噪音——与"用 5 个样本优化提示词"有本质区别。

## 提示词模板版本化（一切的地基）

```sql
CREATE TABLE templates(
  id INTEGER PRIMARY KEY, name TEXT, version INTEGER,
  body TEXT, active INTEGER DEFAULT 0, note TEXT, created_at TEXT,
  UNIQUE(name, version)
);
CREATE TABLE template_stats(   -- 按版本聚合的客观指标
  name TEXT, version INTEGER, date TEXT,
  calls INTEGER, basis_ok INTEGER, basis_bad INTEGER, schema_fail INTEGER,
  PRIMARY KEY (name, version, date)
);
```

每次 AI 调用记录用了哪个 `(name, version)` → 归因数据能按版本分组 → 能对比 v1 vs v2 的
引用有效性 → 改坏了能回滚。**没有这个，「进化」无从谈起**：分不清效果变化是提示词改的还是市场变的。

进化闭环（人在环）：`template_stats` 显示某版本引用有效性下降 → AI 提改进建议 → **用户审核** →
新版本入库 → A/B 对比。全自动进化仅允许朝客观指标，且必须可一键回滚。

## 存储管理（用户特别叮嘱）

`sector_daily` 那次教训（977 板块 × 245 日 = 24 万行/年，无清理会到 820MB/10年）适用于所有按日累积的表。

| 表 | 增长 | 策略 |
|----|------|------|
| `agent_orders` / `agent_positions` | N 账户 × 每日几笔 | 滚动 **365 天** `purge()` |
| `agent_daily`（每账户每日净值） | N × 245/年 | 滚动 **730 天**（净值曲线要长一点） |
| `lessons` | 只记失败，天然稀疏 | **永久**（同 kind 累加 hits 而非新增行） |
| `template_stats` | 模板数 × 版本 × 245/年 | 滚动 **365 天** |
| `agent_runs`（每日循环日志 + LLM 原文） | **最大头**：N × 6 agent × 每天 | 原文滚动 **90 天**，结论滚动 365 天 |

规则：**每张按日累积的表都必须有 `purge()`，且在写入路径后自动调用**；容量在前端可见
（照搬 `/api/sectors` 状态条的 `db_mb` 做法）。`agent_runs` 存 LLM 原文最占空间，
故原文与结论**分表分策略**。

## 分期

| 期 | 内容 | 依赖 |
|----|------|------|
| **一** | 提示词模板版本化（`templates` + `template_stats` + 调用记录版本号） | 无 |
| **二** | agent 日循环骨架（`agent_store` + 流水线 + `SingleDecider` + 多账户） | 一 |
| **三** | 失败归因 → `lessons` 表（闭集 kind + 客观 evidence） | 二 |
| **四** | 教训反哺 5 个已有 agent（`_lesson_block()` 注入，与 `_tier_block`/`_fee_block` 并列） | 三 |
| **五**（可选） | `DebateDecider` + A/B 对比 | 二 |

每期独立可用、可验证。

## 不做（YAGNI）

- **朝收益率的自动提示词进化** —— 样本量决定它只会拟合噪音（见上）。红线。
- **agent 操作真实账户** —— 仅模拟盘。
- **重写 llm.py 的 8 个函数** —— 流水线复用它们，不重造。
- **实时盘中高频决策** —— T+1 下无意义，且样本量不会因此变多（持仓周期才是瓶颈）。
